# 0018 测验 v2.3：中途退出原位续做 + 一组 40 题

日期：2026-10-31。状态：已实现，模拟器验收（待真机）。前作见 [ADR 0017](0017-roommate-v22-device-feedback.md)。

## 背景

v2.2.0 装上手机后（2026-10-31），用户测到一半有事离开，回来发现整组要从头出题：
`QuizViewModel` 的题目、进度、答题结果全在内存里，进程一退就没了，再次进入只能重新
`planDue`，也就可能再发一次 AI 请求。同一轮里用户还指出一组 20 题太短——到期词一多，
每组都要发一次补全请求，费钱也费时间。

用户定了两条：**中途退出原样接着做**（同一组、同一题，不重答、不重问），
**一组 40 题**。舍友设定入口经讨论后决定不动（名字胶囊本来就是入口）。

## 决定

1. **整组题落库，按入口留一行**。Room v13 新增 `quiz_session(mode TEXT PRIMARY KEY, payload TEXT)`，
   主键是 `DUE` / `EARLY`，两个入口各存一份、互不覆盖。`QuizResume`（core.quiz）把题目、
   备用题（答错重练用）、错误词 id、排除集合、第几题、是否在重练、当前选择与对错、得分、
   组号全部序列化成 JSON；`QuizResumeStore` 是唯一读写口。
2. **只在能续做时存，做完就删**。每答一题、切下一题、进入重练都 `persist()` 一次；
   正常结束（`finish`）与没有可测词（`EMPTY`）时按入口删行。写库串行化
   （`Mutex` FIFO），保证后一次进度一定盖住前一次，不会旧状态回写。
3. **作答记录不重写**。每题提交时 `quiz.record` 已经立刻写了 `recall`，续做只是把界面
   恢复到同一题同一状态，不重复计分。恢复时若当前题已答过，仍显示反馈和选项释义，
   等用户按"下一题"。
4. **坏数据一律当没存过**。解码失败、未知 `QuizMode` / 题型、题目为空、索引越界、
   选择下标越界都返回 null，退回正常出题——不能因为一行坏 JSON 把用户卡在"正在准备题目"。
5. **一组 40 题**。`QuizService.SESSION_LIMIT = 40`；AI 补全一次批量上限同步到
   `AiQuizEnricher.MAX_WORDS = 40`，真实超时放宽到 45 秒（一次问的词多了一倍，20 秒不够）。
   今日页"开始测验（N 词）"仍取 `min(候选数, SESSION_LIMIT)`，所以 48 个到期词会说
   40，做完再用"再来一组"接着测剩下的。
6. **今日页入口认得存下的会话**。有 `DUE` 会话时按钮写「继续测验」并保持可用，优先于
   "开始测验（N 词）"；答完最后一题却没点完成时候选数会先归零，只有这一个标志还能把
   用户送回那组题里。判断走 `QuizResumeStore.has(QuizMode.DUE)`（`EXISTS` 查询）。

## 后果

- Room 升到 v13，`QuizSessionMigrationTest` 覆盖 v12→v13（旧库词条与 `quiz_material` 原样
  保留、新表为空），并锁住 DUE / EARLY 两份互不影响。
- `QuizResumeTest` 在 JVM 里锁住四条：同一题同一得分复原、重练中复原仍在重练、
  垃圾数据与越界数据当没存过、未知题型整组丢弃。
- 续做的组跨天也还在：这些题的 `recall` 早在做的时候就写过了，颜色与排期不会因为续做
  再变一次；用户想换一组，做完它就行。
- 一组 40 题的上限由 `QuizServiceTest` 在 JVM 里锁（模拟器与真机词库都凑不出 41 个到期词）。
- 40 题 × 四选项的 JSON 大约几十 KB，一行 SQLite TEXT 足够；仍然只在真正答题时写，
  出题阶段不写。
- 入口标签在模拟器上实测过：答一题后退出，今日页按钮由"开始测验（10 词）"变为「继续测验」，
  点进去回到第 2 题同一组；清掉会话又变回"开始测验（10 词）"。
