# ADR-0005: 跨章连贯靠"一段口述 → 故事圣经 → 逐章变化回报"

- 状态：已采用
- 日期：2026-10-28

## 背景

用户问："万一它写着写着写太长，把前面的剧情忘掉了怎么办。" 这个担心在代码里站得住：ADR-0002 只解决"接得上上一章"——prompt 携带的是同题材**最近 3 章**梗概（`ChapterDao.recentRecaps(genre, 3)`），`story_bibles.synopsis` 每章被**整条覆盖**成上一章内容，角色表 12 条上限、新的挤掉旧的。于是第 50 章对第 1 章一无所知，第 8 章死掉的人可以在第 20 章复活。

另一侧是成本约束（用户："不要用太多"）。算过实际数字：一行章节梗概 60–90 字，60 章全带上也就 4–5 千字，对 DeepSeek flash 档是零点几分钱——"忘掉前面"可以便宜地治掉，分卷摘要那种需要额外调用的方案在当前规模下是过度设计。

## 决定

1. **开局入口 = 一个输入框，不是一轮聊天。** 用户写任意一段想法（一句也行），一次调用把它展开成结构化故事圣经：基调、主角与目标、结局倾向、禁止事项、起始人物表。展开结果逐条可编辑、可删除、可重掷，然后才开始生成章节。明确**不做**对话式多轮开局界面：入口只到"一段话 → 一份圣经"，再往下等于为输入方式再造一个 app，且仍然产出同一份圣经。
2. **三层上下文进 prompt**，取代现在只有 3 章梗概的做法：① 故事圣经全文（含用户手写条目）；② 人物状态表（谁在哪、关系如何、变了什么）；③ 本章全书逐章一行梗概，由旧到新。**超过约 60 章**才把最老的部分折叠成分卷摘要——那时才允许出现"额外一次摘要调用"。
3. **生成契约增加"本章变化"回报字段**：模型必须列出本章里发生状态变化的人物与变化内容，随章节 JSON 一起返回，不额外花调用。系统合并进人物状态表，无需用户维护。
4. **用户写过的条目优先。** 自动合并撞上用户手写设定时不覆盖用户条目，而是在那一行标记"与最新剧情冲突"，让用户看得见它为什么不听话、该改哪句。
5. 因此必须有一个**能看见圣经的入口**（设置页展开当前圣经），否则第 20 章不对劲时用户无从下手。
6. prompt 模板升版到 V3，与 ADR-0002 的 V2 并存记录；schema 新增字段照样必须过 kotlinx-serialization 校验才入库。

## 后果

- 单次生成的 prompt token 上升（圣经 + 人物表 + 全书梗概，千字级），仍远低于分卷摘要方案需要的额外调用成本；每章 API 次数不变。
- 自动维护**不等于**不漂移，只是把漂移概率压低并让冲突可见；用户手写条目的权威性优先于模型回报，这是有意的取舍——宁可偶尔"不听剧情"，也不要悄悄改掉用户设定。
- Room 需承载圣经条目的结构化存储（而非现在的 `synopsis` 单串覆盖），schema 变更要写 Migration 与迁移测试。
- 与 v0.3 的默认密度/篇幅调整同批验证，因为两者都只能靠真机连续生成多章才能判好坏。

## 落地（2026-10-28，v0.3 / versionName 0.3.0）

- 第 1 条：`core.ai.BibleExpander`（一次调用 + ≤2 次修复，超限裁剪：条目 160 字 / 禁止事项 8 条 / 起始人物 12 条）；入口是设置页「查看并编辑故事档案」的单个想法输入框，逐条可编辑、可删、可重掷。**未配置 API key 也能全部手填**——AI 只负责把一段话展开成初稿，不是使用档案的前提条件。
- 第 2 条：`PromptBuilder.VERSION = 3`，渲染顺序即①→②→③；**全书梗概目前全量带上，"超 60 章折叠成分卷摘要"尚未实现**（当前章数远低于阈值，等有真实长篇再写）。
- 第 3 条：章节 schema 增加 `changes: [{who, what}]`，合并逻辑在纯函数 `core.bible.CastMerger`（可单测）；`who`/`what` 任一为空的那条在解析阶段丢弃。缺 `changes` 键的旧 V2 章节行仍照常读。
- 第 4 条：`authoredByUser` 行只标冲突不覆盖，冲突文案「注意：第 N 章把它写成了…」显示在档案行下方；用户亲手改一次即视为解决冲突。
- 第 5、6 条：Room v3 新增 `bible_entries` + `character_states`（`(genre,name)` 唯一）+ `story_bibles.seedText`；旧列 `charactersJson`/`synopsis` 保留但被一次性回填后置空。迁移测试 `StoryBibleMigrationTest` 覆盖 v2→v3 与 v1→v3 两条链路，并在模拟器上的既有数据库上实测过数据存活。
- 实测踩到并已修的坑：同一章里既登场又有变化的人物必须折成一行，否则写 `character_states` 撞唯一索引直接崩；重掷档案时基调/主角/结局这类单行分区不能重复追加读者已写过的同一条。
