# ADR-0002: 跨章剧情连贯的做法

- 状态：已采用
- 日期：2026-10-27

## 背景

用户问"写下一章的功能，能接上前面的剧情吗"。当时的实现只能接上"半章"：故事档案 `story_bibles` 每次生成都用新章梗概**整条覆盖** `synopsis`，人物列 `charactersJson` 从未写入过；prompt 里既没有旧章节的梗概，也没有角色表，模型每章都在重新发明人物与剧情。同时 `ChapterDao` 只有一个按题材取最新章的查询，没有任何"往回看"的入口。

## 决定

1. 章节表新增 `summary` 列（已有），prompt 携带**同题材最近 3 章**的「第N章《标题》：梗概」，按由旧到新排列（`ChapterDao.recentRecaps(genre, 3)`）。
2. 生成契约里加 `characters` 字段：模型必须列出本章登场角色，格式「名字 · 身份」。
3. `story_bibles.charactersJson` 真正用起来：每次保存时把本章新角色与档案旧角色合并去重，**新出现的排在前面**，超过 12 条截断——即"最近出场的优先保留，长期不登场的自动淡出"。
4. 章节编号继续由 `story_bibles.lastChapterNumber` 驱动，因此编号与角色表同为"按题材"两条线，互不污染。
5. prompt 模板升版到 `PromptBuilder.VERSION = 2`。
6. 阅读页改为按当前题材取最新章（`ChapterDao.latest(genre)`），修掉"换了小说类型后阅读页仍显示别的题材章节"的错位；随之删掉不再被调用的 `outline()` / `byId()` / `ChapterHeader`。

## 后果

- 连贯性上限是 3 章 ≈ 2400 字梗概 + 12 个角色，足够中短篇连续剧情；长篇伏笔（第 1 章埋、第 20 章收）超出这个窗口，需要 v1.5 的"故事档案"升级（分卷摘要 / 关键事件表），不能指望现有机制。
- 梗概质量由模型自己负责：它写得含糊，下一章就接得含糊。validator 只保证 `summary` 非空，不保证信息量。
- token 成本随窗口线性上升；3 章是"能接上剧情"和"每章 prompt 不膨胀"之间的折中，若用户觉得还是失忆，把 `RECAP_CHAPTERS` 调大即可，无需改结构。
- 角色淡出策略意味着如果某角色消失 12 章以上，它可能被彻底挤出档案，再登场时模型会当成新角色——可接受，因为读者也忘了。
