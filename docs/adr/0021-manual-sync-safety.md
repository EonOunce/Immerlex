# 0021 多设备手动同步的安全闸门（v2.6）

## 背景

用户要手机 + 平板两边学，但项目没有、也不打算有服务器。产品早先定下的同步模型是
**手动单活跃设备**：在一个设备上学，学完上传；换设备时先下载再学。传输仍走已有的
坚果云 WebDAV（ADR 0006）。

这条模型的风险只有一个但足够毁掉所有记录：**下载会把整台机器的库换成云端那一份文件**。
WebDAV 没有版本历史，设备时钟也互不可信（本机曾因模拟器时区是 GMT 差 8 小时），
所以"谁更新"不能靠时间戳判断。

## 决定

1. **血缘是本机唯一的判定依据**。Room v14 新增单行表 `sync_lineage`：最后一次与云端
   一致的备份名（`syncedName`）、当时本机的词/章/复习记录数与最后一条记录 id、
   最后一次上传与最后一次恢复的名字和时刻。丢了这条记录，判定退化成"问用户"。
2. **下载前先判三种结果**（纯函数 `core.backup.SyncGuard.verdict`）：
   - `NothingToLose`：本机是空机器，下载是纯得到；
   - `InSync`：本机指纹与上次同步记录完全一致，放心下载；
   - `LocalUnsynced`：本机有同步之后才产生的记录 → **绝不静默下载**，界面必须让用户
     在"先上传"和"仍然下载"之间选，并报清楚会丢多少个词 / 章 / 复习记录。
   撤销会让数目往回走，所以差值按 0 兜底，不报负数。
3. **上传永远安全**，文件名自带来历：`immerlex-<日期>T<时分秒>-<设备>-v<库版本>.db.gz`
   （`core.backup.BackupNaming`）。同一天再传一次不会顶掉上一份；旧命名（只有日期）
   仍能识别，但读不出设备与库版本。
4. **保留策略按份数**（`Retention`）：最近 60 份 + 每个更早月份最新的那一份。
   月末那份不受上限约束，它是"上个月确实存在过"的唯一凭据。
5. **覆盖本机库之前先留安全快照**（`core.backup.SafetyCopies`）：当前库 gzip 到
   `filesDir/restore-safety/`，保留最近 3 份。放 `filesDir` 不放 `cacheDir`——缓存会被
   系统清掉，被清掉的安全快照等于没留。
6. 恢复流程本身仍是 ADR 0006 那一道闸：校验 gzip 头 / `user_version` / `integrity_check`
   / 必备表，不过就逐项明说且不动本机库；过了才换文件并强制重开应用。

## 后果

- 两台设备交替使用时，每次切换只有两步（学完上传、学前下载）；判为 `LocalUnsynced`
  时多一次确认，但不会被一个误触覆盖掉当天所有记录。
- 血缘记录只存在于本机与它上传的备份里，换机、恢复旧备份后第一次同步会按"问用户"处理——
  这是有意的保守选择。
- 安全快照只在本机看得见，云端仍然只有一份份备份文件；它解决"拉错一份"而不是"云端丢文件"。
- 相关测试：`SyncGuardTest`（判定矩阵）、`BackupPlanTest`（命名与保留）、
  `SyncLineageMigrationTest`（v13→v14、v1→v14 全链）。
