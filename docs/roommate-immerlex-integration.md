## 2. 用户已经决定的词间配置

| 项目 | 决定 |
|---|---|
| 角色 | 同住、会打工出门交朋友的小室友；不是奇幻探险伙伴 |
| 体验优先级 | 生活与惊喜最重要，同时有陪伴、养成和装扮意愿 |
| 货币显示名 | 小鱼干 |
| 获得与消费 | 背单词获得，可送礼、买室友作品；不是只做里程碑赠品 |
| 非实物 | 可有微个性、口头禅、习惯或动作相关内容 |
| 自主成长 | 也能免费从学过的词、共同经历、自主生活中习得；函数控制频率 |
| 人格 | 开始选维度→生成具体性格卡；稳定底色＋经历影响 |
| 互动 | 见闻、提问、选择、送礼、摆摊、作品、小计划、自主行为混合 |
| 记忆 | 持久人物、朋友、共同选择和未完事项；不是每次生成整份新人设 |
| 素材 | 用户提供 EmoteLab 制作的封阳君 GIF；现用 AI API 不生成图片 |
| 设备 | 另一台安卓手机接续；没有提出 Windows、iOS 或实时多人需求 |
| 云端 | 希望利用坚果云保存并接续整个生活存档 |

普通陪伴免费，新动作不必花钱；用户已认可少量共同小计划和有后续的礼物。不要重新退回“不给积分，只按稳定词数长大”的旧建议。最初讨论中“到期日超过三天代表稳定掌握且刷不出来”的说法不应作为奖励依据：到期日随时间变化，评分也不能证明真实掌握。

建议但未最终确认的数值，v2.0 先按演示值实现：每日收益 `min(N,30)+5*[N>=5]`、商品价格（见 `RoomCatalog`）、入口（今日页卡片）。主故事份数、习惯原型参数、单活跃设备交接仍未定。固定公式可用于演示，不代表用户已批准正式平衡值。

### 3.1 必须保留的学习规则

- learn 是首次接触；recall 是真实独立回忆；看释义和当堂重练不写回忆记录。
- 提前复习允许继续记真实 recall；奖励的每日单位去重不得变成复习次数上限。
- 复习模式未到期词“想起来了”不记账，“没想起来”可记一次 AGAIN；室友不改变这个边界。
- 不改 FSRS 数学、参考向量、rating、到期队列，也不为宠物另建一张单词调度卡。
- 室友关闭、没有API、云端失败时，词库、阅读、测验、计分、撤销仍可正常使用。

### 3.2 事务边界（2026-10-30 已补）

原缺口：[ScheduleService.kt:165](../app/src/main/java/com/immerlex/core/schedule/ScheduleService.kt#L165) 先更新词卡再插入日志；[撤销入口:122](../app/src/main/java/com/immerlex/core/schedule/ScheduleService.kt#L122) 先恢复词卡再删日志。当前用进程内 Mutex 串行，不是覆盖两次 DAO 写入的 Room 事务。

v2.0 已把 `learn` / `recall` / `undo` 的多步写入收进 `database.withTransaction`（`write()`），卡片与日志同生同死。没有引入消息总线，FSRS 与评分算法未动。

## 5. 词间学习适配与小鱼干

建议口径：系统启用之后，确实存在且超过撤销窗口的 `learn` 或 `recall`。同一日同一英文词跨章节、测验、题型、重复回忆只计一次；答错也算，纯查看不算。

- `eventId` 使用存档命名空间＋日志身份，不能把不同独立安装的本地自增数字当全球唯一。
- 每日单位采用宿主既定词条规范化身份，并保存必要的词形快照；只用自增 wordId 会让删除重导同词绕过去重。不要擅自把不同词形、词义全合并成同一个词。
- 活动归属日按发生时的日期记录，8秒后过了午夜也不能把昨天的活动算到今天。
- 等待撤销期的小鱼干不可花；到期重新核实源日志，以唯一约束和事务发放。进程被杀后可重新扫描待确认记录，不能少发或多发。
- 若启用时有大量历史记录，默认从启用时间起处理，不突然追溯发全部历史收益。
- 同一词当天的某条日志撤销但还有其他有效正式记录时，不能误删该词当天资格；反之最后一条有效来源撤销则不结算。
- 最终计数与今日热力图可能因“等待8秒、启用边界、规范化去重、奖励上限”而不同，应在规则页明确；不得直接把热力图颜色当钱包事实。

规则未最终确认前用测试账户和配置展示：5词→10小鱼干，20词→25，30词及以上→35；让用户体验消费周期后再锁定。

## 6. 素材与第一段演示

素材来源：2026-10-30 用户明确「测试文件我另外给，不要用封阳君的」。封阳君那份**不接入**，也不作为演示或测试的依赖；用户另行给一个文件夹。应用做成**素材包导入**（SAF 选目录、持久化授权、按文件名做动作标签、接入前逐张预览）。任何素材路径都只在该用户机器上成立，不能写死进产品代码或通用手册的运行依赖。

从旧素材观察到过工作、驾驶、吉他、喝饮料、吃甜甜圈、打招呼、礼物、记录、摸头、睡觉等命名，可当作**命名约定**的参考；但不能假设新素材包有同样的动作、同样的命名，也不能假设能换装或走路。导入时先只读建立清单和代表性预览，原文件不改名、不覆盖、不移动。

用户 2026-10-30 改为 GIF **循环播放**（取代 v2.0 的单次停末帧）：动作一旦触发就持续循环，直到换成另一个动作或离开页面。播放中同一互动的连点不重启、不排队、不额外请求 AI 或重复扣款。完整契约见通用手册第 9.1 节。

Compose 重组、重新收集状态和前后台切换不得成为新的播放触发或导致重启；用稳定的互动/镜头身份区分重绘与新动作。API 28+ 显式使用 `REPEAT_INFINITE`，26–27 用无限 `ValueAnimator` 兜底，不依赖图片组件默认循环；动画回调必须回主线程注册。

演示建议：

1. 用户设置“说话直白、做事慢、表情丰富”等维度，看到可调整的具体性格卡。
2. 初次进入，室友打招呼；摸头有回应，不花小鱼干。
3. 演示账户完成5个不同词的合格活动，等待撤销窗口后看到10小鱼干。
4. 次日围绕 rehearsal / hesitate / applause 出现吉他小事件；不要求把三个词硬塞进每一句话。
5. 用户选“找个搭档”，下一段有同一个朋友的后续；同时可以给室友送礼或买有正文的创作。
6. 多日相关尝试进入习惯证据，正式习得前只是偶尔动作；不能刚出现一次吉他就自动变成音乐家。
7. 断网时仍可看旧故事、摸头、学习和记账，新故事显示等待而非虚构成功。

这七步用明确标记的演示存档和可控时间完成；演示内容不进用户真实数据，不篡改真实复习状态。

## 7. 备份现状：旧手册与代码不一致

核对事实：

- [DbSnapshot.take:39](../app/src/main/java/com/immerlex/core/backup/DbSnapshot.kt#L39) 实际执行 `wal_checkpoint(TRUNCATE)` 后直接读取主库压缩，不是旧手册多处写的 `VACUUM INTO`。
- [BackupService.upload:127](../app/src/main/java/com/immerlex/core/backup/BackupService.kt#L127) 会校验解压后的库再上传；这种校验不能替代在并发写入下获取一致性快照的机制。
- [DbSnapshot.install:108](../app/src/main/java/com/immerlex/core/backup/DbSnapshot.kt#L108) 现在委托 `core.db.DbFileSwap`：新库复制成 `.new` 暂存 → 旧主库与 `-wal`/`-shm` 改名 `.prev` → 就位后才删；失败回滚，进程被杀由开库前 `recover()` 收尾（`DbFileSwapTest` 锁住回滚）。
- [BackupService.restore:98](../app/src/main/java/com/immerlex/core/backup/BackupService.kt#L98) 关闭连接后整库替换，需要重开应用；当前不是业务级合并。
- 备份是整份 immerlex.db，不含外置 GIF、SharedPreferences、AI key 或 WebDAV 密钥。新手机需配置连接与密钥；恢复不等于设置同步。
- 自动上传不是自动接续，更不是两台手机并发修改后合并。

第 3 项已在 v2.0 修补（`DbFileSwap` 换文件 + 失败回滚 + 开库前恢复）。第 1、2、4–6 项仍未做，验收前必须补齐：

1. 采用在目标 Android/SQLite 版本上实际支持的一致性快照方案；若使用 VACUUM INTO，先验证 minSdk 26 对应设备能力，不可因为文档曾写过就直接调用。
2. 快照获取、并发学习、恢复停写与后台 worker 有明确互斥/生命周期策略，不能仅靠备份服务自己的 Mutex 阻止其他模块写库。
3. 恢复前保留可验证的旧库；切换失败能回滚。测试包括磁盘不足、复制中断、旧WAL、连接未释放。（v2.0 已做换文件与回滚，`DbFileSwapTest`；磁盘不足等失败路径仍待补测。）
4. 检查按备份schema版本应有的室友表和引用，不能只验证最老三张表后宣称室友存档完整。
5. 加入素材清单和按内容去重的媒体传输，核实实际数据量；不得继续套用未含GIF的月流量估算。
6. 在任何用户真机覆盖恢复前得到当次明确授权，并保有独立可恢复副本。

## 8. 另一台安卓手机接续：必须先明确的体验

用户确认需要另一台安卓手机继续相处，但尚未决定是否必须自动或能否两台同时离线使用。

推荐最小安全交付：先完成完整备份恢复，再提供显式“在另一台继续”的单活跃设备交接。解释给用户的是：A存好并交接，B确认后接着过日子，A不再偷偷上传旧故事；不是让用户选择数据库或同步算法。

先确认接续范围：

- 若沿用整库快照，B手机的词库、章节、学习记录也会随A替换，不能只说“恢复宠物”。必须在操作前明确展示影响并备份B。
- 若用户要求保留B原有学习库、只接室友，需独立导出室友存档和来源活动命名空间；这是额外范围，不能靠直接恢复整库完成。
- WebDAV条件写入/锁等能力须真实账号小文件实测；无能力时采用明确手动接续，不宣称自动无冲突。
- 两台同时消费同一余额不得以余额相加或最后写入覆盖收场。未实现冲突策略前，不承诺多写者。

接续至少保留固定角色ID、事件与选择、朋友、习惯证据与当天决策、小鱼干流水、库存、作品、规则版本、启用时间与奖励去重记录，以及媒体引用；原机不再拥有写入权时不能绕过限制继续消费共享钱包。
